## Known gaps + deliberate choices (recorded, not forgotten)
- **`send_frame.mjs --self-test` is OPT-IN, not part of the default gate.** It is the ONLY coverage of the CLI-side delete->frame->sidecar ordering and byte content (~144 checks) and `npm run ci` (tsc + `scripts/*.test.js`) did not run it, so that coverage could not fail a build. `scripts/send-frame-selftest.test.js` now wires it in, SKIPPED unless `RUN_SEND_FRAME_SELFTEST=1`: the self-test binds ephemeral HTTP/WS sockets, T2 polls a ~900 ms window and T3b enforces a 300 ms handshake deadline, and a flake there would redden a gate whose value is that red means something. Arm it whenever `send_frame.mjs`, the WS upload protocol or the sidecar ordering changes: `RUN_SEND_FRAME_SELFTEST=1 npm run ci` (verified locally: skipped by default, passes in ~1.3 s when armed).
- **`MAX_EPUB_BYTES` is 8 MiB and that is a TRANSPORT limit, not a format one.** `uploadLocalFileToCrossPoint` (`crosspoint_upload.ts:191`) does not stream — it materialises the whole file as a base64 STRING and again as a `Uint8Array`, ~2.4x the book live at once, which is an OOM process CRASH on Hermes/Android (no error result to show). The number is derived from that allocation shape, NOT measured on the paired phone (reader offline for this work). RAISE IT ONLY after the shared transport streams straight into the 4 KB WS frames it already sends. Related hole, unclosed: the size guard is SKIPPED when the picker reports no size (common for Android SAF picks — the case most likely to crash); closing it means stat-ing the copied cache file, which belongs behind the transport seam.
- **Books moved from `/send-to-x4` to `/books`** (the old `settings.DEFAULTS.articleFolder` -> `epub_sender.BOOKS_DIR`) with no migration. DeviceScreen now scans BOTH and labels the legacy root when it has content, so older books stay listed and deletable; nothing writes `/send-to-x4` any more. **NARROWING, recorded so it is not re-found as a regression: the merged LIBRARY list (`services/library.ts`) lists `/books` ONLY.** Legacy-root books appear in the collapsed "All files" section and are deletable from there, but not from the library list above it. The blocker is NOT the mkdir side-effect (`listCrossPointFiles` ensures its folder, but a plain `GET /api/files?path=/send-to-x4` creates nothing — `DeviceScreen.fetchDirectoryItems` proves it); it is that `LibraryBook` carries no folder, and the reader-side delete deliberately resolves a row against the FLAT `/books` listing (`findReaderFile(..., preferRoot)`) precisely because a name present under both roots is otherwise ambiguous — the mtime-ordered merge used to delete the legacy copy silently. Switching the legacy root on therefore means threading a per-row folder hint through the merge, the AsyncStorage cache and the delete path, and re-testing all three. `/api/files` does not filter dotfiles, so a listing that disagrees with the reader's own browser is always a hidden-name bug — `resolveEpubFilename` now strips leading dots for exactly that reason.
- **Two live sleep-screen writers, one folder each.** `uploadScreensaverToCrossPoint` (`crosspoint_upload.ts`) writes `/sleep`; `wallpaper_sender` writes `/.sleep` (the firmware prefers it — `SleepActivity` reads `/.sleep` first, `/sleep` as fallback). DeviceScreen's Screensavers section now scans both so Wallpaper-tab uploads are visible and deletable. CONSOLIDATING the writers onto `/.sleep` is still unclaimed work; until then, do not "simplify" either root out of the scan.

## Device facts (VERIFIED on hardware)
- X3 = ESP32-C3, panel 792x528 landscape, 1-bit.
- **Love-note frame** = `/.love-notes/current.frame`, EXACTLY **52272 bytes** (528 rows x 99 B/row), MSB-first, 1=white/0=black, row 0 = landscape TOP. **NO X-MIRROR** — stored bit j IS panel pixel x = j, packed left-to-right, so panel x=0 is the MSB of byte 0. The app composes in PORTRAIT 528x792 and maps into the 792x528 landscape buffer with a **90-degree COUNTER-CLOCKWISE** rotation: `lx = py`, `ly = 527 - px` (inverse `py = lx`, `px = 527 - ly`). CCW is the DEFAULT (`DEFAULT_FRAME_ROTATION` in `src/device/x3.ts`); `cw` stays selectable and renders exactly 180 deg off. Firmware raw-blits it; it's TEMPORARY (dismiss returns to reading). Firmware side done: `MessageDisplayActivity`. **ALL PROVEN ON A PHYSICAL X3, 2026-07-28** — the earlier `j = 791 - x` mirror rendered mirrored, and `cw` rendered upside-down. Any older doc/comment claiming X-mirror or a cw default is stale.
- **Uploads must DELETE FIRST.** The firmware REFUSES to overwrite an existing path (`ERROR: File already exists`) and writes nothing. This bites every path that re-writes a FIXED name: `/.love-notes/current.frame` is one slot re-sent on every note, `/sleep.bmp` is one slot re-sent on every "Set sleep screen", and `promote` mints a DETERMINISTIC `/.sleep/<name>.bmp` per history row. A sender with no delete therefore works exactly once per name and then silently leaves the OLD image on the panel. So: `POST /delete` (form `path` + `type=file`), tolerating a delete of a missing file (404 on a first send is NORMAL), THEN upload. Implemented in `love_note_sender.ts`, `wallpaper_sender.ts` (`sendWallpaperBmp` — covers primary, set and `promote`) and `scripts/send_frame.mjs` (default on, `--no-delete` opts out). Pinned by `send_frame.mjs --self-test` T7/T7b/T7c and by `scripts/wallpaper-sender.test.js`'s `fakeDevice`, both of which enforce the same exists-rejection — a plain accept-everything mock cannot see this bug.
- **Wallpaper (permanent)** = 8-bit grayscale BMP (BI_RGB uncompressed, 256-entry gray palette) -> upload to `/sleep.bmp` (or `/.sleep/<n>.bmp` = rotating set). **NO rotation** on this path (firmware `drawBitmap` is orientation-aware) — that, not mirroring, is what differs from the love-note frame; neither path X-mirrors. Requires sleep mode = CUSTOM on device.
- **Transport (all WiFi)** = existing `src/services/crosspoint_upload.ts`: WS :81 chunked (`START:file:size:path`->`READY`->4KB chunks->`DONE`), `GET /api/files`, `POST /mkdir`, `POST /delete`. Reader at `crosspoint.local` (LAN) or its AP `CrossPoint-Reader` (open today).
- **Roles**: HOST (paired, direct access) owns PERMANENT state (wallpaper/epubs/settings) + relays messages; CLIENT (partner, remote) sends TEMPORARY love-notes via mailbox only.

## Build / run (Android; this devbox is on tailnet 100.77.36.51)
- **Node 20 REQUIRED**: `nvm use 20` (box default is 24; repo `.nvmrc` pins 20, `package.json` `engines` says `>=20 <21`). `scripts/ci-remote.sh` now ENFORCES this on the CI host too — it reads `.nvmrc`, `nvm use`s that version and exits **96** rather than validating on whatever node the host defaults to (server-mac's own default is v26). If node 20 is ever genuinely dropped, change `.nvmrc`, `engines` and this line together — the gate reads `.nvmrc`, so they cannot drift apart silently any more.
- **`expo-document-picker` (~14.0.8, autolinked) is in `package.json` AND now in `package-lock.json`, but is NOT installed in this devbox's `node_modules`.** The lock was out of sync (the messenger cleanup regenerated it while the dep was dropped; the epub builder re-added it to package.json only), so `npm ci` refused the tree with `EUSAGE ... Missing: expo-document-picker@14.0.8 from lock file` — latent, because `scripts/ci-remote.sh:110` keys install on `shasum(package-lock.json)-node` and had been printing "node_modules up to date, skipping npm ci". Fixed with `npm install --package-lock-only` (lockfile only, +12 lines, no other package re-resolved — deliberately NOT a real install, per this box's resource rules). **Run `npm install` locally before the native dev-client rebuild**: the module is autolinked, so prebuild/gradle need it actually present. CI installs it itself on the changed lock hash.
- Dev-client APK: `cd android && ./gradlew assembleDebug` -> `app/build/outputs/apk/debug/app-debug.apk`; sideload to phone.
- Metro: `npx expo start --dev-client` (phone connects over tailnet).
- Native modules present -> NOT Expo Go.

## Gotchas
- `android/` is Expo prebuild output (gitignored). Low-memory Gradle tuning is in `android/gradle.properties` (serial, `workers.max=2`, 4G heap, no daemon). `expo prebuild --clean` REGENERATES `android/` and LOSES it -> to persist, move into `app.json` (`expo.android`) or a config plugin.
- A parallel build OOM/hung this box at 2G heap; serial config fixes it but the FIRST native build is slow (~15-25 min), incremental after.
- iOS: needs `server-mac` (trust its ssh host key first); cannot build on this Linux box.
